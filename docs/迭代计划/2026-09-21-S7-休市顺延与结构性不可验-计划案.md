# S7 计划案：短期预测休市顺延 + 结构性不可验归因（未开工）

**为什么必须做**：`还有哪些待验证的板块都可以验证完` 这条要求今天没达成。24 条到期未验证里，
至少一类是系统判据缺陷而不是缺数据（详见 `2026-09-21-S4a-v7.4-代码评审修订.md` §二十）。

**根因（已实测复现）**：`prediction_verify_service._check_fund_data_availability` 数
`[prediction_date, target_date]` 区间内的净值条数，`< VERIFY_MIN_DATA_POINTS`（=2）即判
"基金数据不足"。预测 1709（512680，周期 1 天，目标 2026-07-11 **周六**）区间内只有 1 条
（07-10），因此**永远达不到 2 条**；而 515440/158038 向数据源要那段区间返回 0 条，
是**真·没有历史**。两类现在都归"还能再试"，于是 `unverifiable` 恒为 0、Cron 每天空转，
提示语还用 `days_behind = 窗口终点 - 全库最新净值日` 算出负数说"请更新基金数据"。

**改动（三处，按顺序，每步带用例）**：
1. **休市顺延**：目标日没有净值时，终点取"目标日之后第一个有净值的交易日"（1709 → 07-13），
   窗口点数按顺延后的区间计；顺延幅度设上限（建议 ≤ `window_days_after`），超上限按缺历史处理。
   验收：1709 能出结论；已有 647 条用例全绿；新增用例覆盖"目标=周六""目标=周日""连休 3 天"
   "顺延超过上限""真无历史"五种。
2. **结构性不可验归因**：`data_points` 不足且源端确认无该区间历史时，落入 `unverifiable`
   并写明原因，`prediction_lifecycle.count_by_lifecycle` 不再恒报 0、Cron 不再重试。
   验收：515440/158038 的预测变成带原因的"不可验"，而不是每天的 pending。
3. **提示语分诊**：区分"休市顺延后可验 / 缺历史不可验 / 净值确实太旧该更新"，
   `days_behind < 0` 时**禁止**再输出"请更新基金数据"。
   验收：三条文案各有断言的用例。

**风险与护栏**：`prediction_verify_service.py` 是 AGENTS.md 标注的准确率核心。
先复制一份本地库做对照跑（改前/改后各自的 判对/判错 计数与差异清单），差异必须能逐条解释；
所有写入走已有备份 + `run_id` 机制。不碰生产。

**自评分项（要 ≥90 才动手）**：根因是否用真数据复现；是否区分了两种性质；
回归对照是否可比；用例是否覆盖边界；是否给 `unverifiable` 留了人工复核出口。

# 计划案 v2（第 1 轮评审 62 分未过，按建议重写；根因判断已更正）

评审用真数据推翻了 v1 的前提，两处必须写在这里避免下次又照错的做：

1. **"顺延到下一个净值日"违反仓库既定策略。** `prediction_verify_service.py:770-773` 明写
   "验证窗口固定截止到 target_date，**禁止使用目标日之后的行情**"；
   `tests/unit/test_prediction_verify_date_boundary.py:133`（`test_weekend_target_accepts_friday_nav`）
   断言周末目标日取**周五**净值、:96/:109/:244 同义，且 `prediction_utils.py:333-345` 已有**向前**兜底。
   所以休市本身不会导致不可验证，v1 的"前向顺延"是在跟防未来函数的护栏对撞。
2. **1709 真正的根因更窄**：`VERIFY_MIN_DATA_POINTS=2` 要求 `[prediction_date, target]` 内
   **至少 2 条净值**，而这条预测 `prediction_date=07-10(周五)`、`target=07-11(周六)`，
   窗口**物理上只可能有 1 条** ⇒ 任何 1 天期、起点到目标之间只跨 1 个交易日的预测都永远不达标。
   这不是周末问题，是**门槛没按窗口容量缩放**。

## v2 改动（四处，都不引入未来数据）

- **S7-a 门槛随窗口容量缩放**：`min_data_points` 生效前先算窗口内**可交易天数**（以该基金
  自己的净值日历为准，不用 weekday 猜测：国庆连休、周度净值的 QDII/定开都盖不住），
  要求 `data_points >= min(VERIFY_MIN_DATA_POINTS, 窗口内可交易天数)`，且下限仍为 1；
  只有 1 个点时**不得**据此判"数据不足"，改由既有的 `VERIFY_MAX_END_NAV_AGE_DAYS`（终点净值陈旧度）
  与起点净值可得性把关。新增配置 `VERIFY_MIN_WINDOW_TRADING_DAYS`（默认 1）而不是复用
  `window_days_after`（1 天档只有 1，用它当上限会让 1709 继续被拒——v1 就死在这）。
- **S7-b 真·缺历史要能证明再去标**：003033 的本地净值全在 **2020-11-11~2020-12-08**，
  而 `fund_api.py:812-825` 因为"最早日 ≤ 起点 + 窗口 <14 天"直接 early-return，
  **从没问过数据源** ⇒ v1 说的"源端确认无历史"对这 3 行是未证明的。改为：判定结构性不可验之前，
  必须真的向源请求过该区间（带负结果缓存，避免每天重试），并记录"已请求区间 + 返回条数"。
- **S7-c 新的不可验状态换个名字**：`retention_three_buckets.py` 已有
  `BUCKET_UNVERIFIABLE="unverifiable_predictions"`（到期 ≥90 天无结论，属**删除候选集**）。
  新状态命名 `data_unverifiable`（存 `verify_history` 派生规则还是新列要明确写清，
  生产 `ENABLE_STARTUP_MIGRATIONS=false` 需单独迁移脚本），并提供"历史补齐后自动解除"的路径。
  **要让 Cron 停止重试，改的是 `filter_due_for_verify`**，不是 `classify()`
  （`filter_unverifiable` 现在按设计恒空，`test_prediction_lifecycle.py:156`、
  `test_prediction_query.py:173/369/383/391`、`prediction_query_service.py:258` 都钉着旧行为）。
- **S7-d 提示语**：`days_behind<0` 时不得再说"请更新基金数据"（v1 说"删除矛盾句"，其实
  `:376-384` 的 `stale_hint` 已经做了一半）；补 `data_points==1 且窗口只有 1 个可交易日`
  这一类的专属文案。

## 必须先做的第 0 步（只读分诊，别再靠猜）

并要求三类相加正好等于 24、给出明确终态（例：`24 = 10 等净值 + 1 门槛缩放后可验 + 13 数据不可得`）。

## 缓存与一致性的坑（评审补的，v1 完全没写）

`_check_fund_data_availability` 里 `fund_code in _history` 时**只用缓存**，过滤为空就返回 0 条、
不回落到 DB（`:331-346`），而 `_warm_cache` 只装 `today-120d ~ +14d`（`:1169-1170`）
⇒ **批量验证可能报"0 点"而单条验证有数据**。必须补一条"窗口 >120 天时 批量==单条"的用例。

## 准确率漂移闸门（这是改判据，必须能证明没偷偷改历史结论）

`routes/predictions.py:148` 的 `rollback_invalid_verifications(min_data_points=2)` 吃同一个门槛；
**已有 77 条已验证记录的 target 落在周末**。所以 S7-a 合入前要在**库副本**上跑改前/改后快照
（每个博主的判对/判错、`blogger_stats`、`prediction_groups`），差异逐条解释，**零未解释差异**才允许合。

## 回滚要说实话

`scripts/restore_prediction_batch.py` 的 `RESTORE_FIELDS` 含 `target_date`/`is_correct`，
**不含 `verify_history` 与新列**；另有一个老的 `scripts/_tmp_shift_weekend_targets.py` 直接改
`target_date` 且**不写 change log、没有 run_id**。v2 明确：任何改写历史目标日的动作都必须走
`prediction_change_log_service` + `run_id`，并把那个临时脚本退役。

## 对老板怎么标（避免"验了但不是他预测的那天"）

1 天期预测若窗口只有 1 个净值日，结论要带**低证据标记**并在详情里写明
"窗口只有 07-10 一条净值，按 07-10 与起点比较判定"；不得静默计入准确率大盘，
也不得写成"已按原目标日验证"。
