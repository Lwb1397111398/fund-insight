## 十、老板 2026-09-20 补充指示（v3.1，**优先级高于本文其他设计**）

### 10.1 授权：正确数据可以直接覆盖线上

> "你可以把修改后的正确的数据上传覆盖原数据，反正是正确的就没问题。"

- §七 的"生产回写需老板确认"这一条**解除**：修好的数据可由我直接写回生产。
- 但仍**不用**整库覆盖导入（`/api/config/import replace=True`）：它会先 TRUNCATE 再导入，且生产在 `CRAWLER_ENABLED=true` 下会持续新增帖子/预测，整库覆盖会把导出之后线上新产生的内容静默抹掉——那不是我改出来的"正确数据"，属于误伤。
- 落地口径：**定向写回**（`sector_fund_mapping`/`sector_alias` upsert + `sync_sector_mappings` 在生产重放），效果等价于"用正确数据覆盖"，但不丢线上增量。执行前先做一次生产备份（`scripts/backup_database.py` 同构逻辑），并保留 `run_id` 以便回滚。

### 10.2 选基规则（必须进 prompt、进判定、进金标集）

> "有些是无奈之举，比如 债券→512000 证券ETF、SpaceX→159206 军工ETF，是因为没有专门的基金，这是关联性最大的了。选基金最好是 ETF，因为最纯粹，其次才是其他的，没有 ETF 的时候才选择其他的。"

这推翻了 v1/v2 里"零字面重合即疑似错配"的默认怀疑：那 68 条里有老板**有意为之的代理映射**。因此：

1. **品种优先级（硬性）**：`ETF（159xxx / 51xxxx / 56x / 58x 等场内指数）` > `LOF / 场外指数基金（16xxxx / 00xxxx / 01xxxx）` > `主动管理型`（仅在无任何指数产品可选时接受，且 `confidence` 打折 0.85）。
   - T1 的 prompt 明写这条优先级，并要求 LLM 对每个候选标注 `is_etf`；
   - 排序键：`(是否直接对应, 是否 ETF, T3 分数, name_sim)`，即**同一板块有直接对应的 ETF 时，永远不选场外/主动**。
2. **代理映射（proxy）成为一等公民**：`match_kind ∈ {direct, proxy}`。
   - `direct` = 存在与该板块语义一致的基金（例：半导体芯片 → 159995 芯片ETF）；
   - `proxy` = 该板块**没有专门基金**，选的是关联性最大的可得标的（例：债券 → 512000 证券ETF、SpaceX → 159206 军工ETF、日股 → 日经 ETF）；
   - 判定顺序：先穷尽 direct（T1 提案 + T4 关键词搜索都试过且都不通过）才允许落 `proxy`；`proxy` 必须写 `verify_message='无对口基金，取关联度最大的替代：<理由>'`，前端用**不同颜色徽章**显示"替代标的"，与"错配"区分开，老板一眼能看懂这不是 bug。
   - **`proxy` 不因"名称与板块零重合"被自动判错**；相反，agent 要先证明"确无对口基金"，因此它的证据链必须包含 T4 搜索过的关键词与返回结果（可复核）。
3. **禁止把 proxy 当挡箭牌**：`no_fund`（连替代都找不到）与 `proxy`（有最优替代）必须分开；`needs_review` 只用于"LLM 与验证结论冲突、或同类 direct 候选分数接近"的情况。
4. **金标集 `gold-standard-50.md` 相应调整**：至少 10 条是**已知有意代理**（含 债券/SpaceX/豆粕/日股 等），期望 agent 结论为 `proxy` 且保留现选择，而不是把它改错；门禁新增一条硬指标——**金标集中标注为"有意代理"的条目，agent 不得改判为别的基金**（改判数 = 0）。
5. **零重合清单的语义更正**：`docs/迭代计划/baseline-2026-09-20.md` 第五节标题的"疑似八竿子打不着"读起来像判决书；实际它是**待复核工单**，其中老板已确认的有意代理在 S4 后应转为 `match_kind='proxy'` + `reviewed=true`，而不是被"修正"。我会在该文件顶部补一行口径说明。
