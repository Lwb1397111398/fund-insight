# 基金数据抓取与验证

## 职责一句话
从天天基金/东方财富取基金基本信息与历史净值，并回答两个问题：这只基金**真的存在、抓得到数据**吗？
它**是不是基金**（不是股票）？

## 运作流程
1. `FundAPI.get_fund_info(code, allow_fallback=True)`：`fundgz.1234567.com.cn/js/{code}.js` 取实时净值；
   `allow_fallback=True` 时会退回历史净值接口补数据（**验证场景必须传 False**，否则任何代码都能"通过"）。
2. `get_fund_history(code, days)` / `get_fund_history_range`：f10 历史净值分页，页间 `sleep(0.2)` 节流。
3. `verify_fund_fetchable(code, input_name, probe_stock=False, fill_name=True)`：
   - `ok`（旧语义，前端面板依赖）：有净值 **或** 有任意历史；
   - `is_strict_ok`（agent 用）：`nav>0` **或** 历史 ≥5 条（历史窗口取 30 天，7 天遇节假日只有 4–5 条会随机翻转）；
   - `kind`：基金域有数据即 `fund`；无数据且 `probe_stock=True` 才去东财行情接口探测，命中判 `stock`；
   - `official_name`：实时接口缺名时用 `search_fund(code)` 反查官方名回填（场内 ETF 经常拿不到实时名）。
4. `verify_funds_batch(items, delay)`：批量验证，相同代码只请求一次；`fill_name=False` 避免额外请求。
5. `search_fund(keyword)`：天天基金搜索接口，返回天然只含基金（`fund_code/fund_name/fund_type`）。
6. 入库：`FundDataManager.update_fund_info/update_fund_history` → `fund_info` + `fund_history`；
   `FundSyncManager` 按预测/板块决定该同步哪些基金；`fund_update_task.py` 提供后台任务状态。

外网：`fundgz.1234567.com.cn`、`api.fund.eastmoney.com`（f10）、`fundsuggest.eastmoney.com`、
`push2.eastmoney.com`（股票域探测，仅在 `probe_stock=True` 时）。本地：`fund_info`、`fund_history`。

## 关键数据结构
`fund_info`：`fund_code`(主键)、`fund_name`、`fund_type`、`sector_type`(自由文本)、`latest_nav`、
`nav_date`、涨跌字段、`active_predictions`、`can_delete`。
`fund_history`：`fund_code` + `nav_date` 唯一，含 `data_quality`/`quality_note`。

## 已知坑与约束
- **`fund_info.fund_type` 实测 162/162 为 NULL**：`jsonpgz` 载荷里没有 fundtype，
  所以"类型判定"目前只能靠基金名关键字 + `search_fund` 的 `FUNDTYPE`（该字段实测常为空串）。
  需要类型时先回填，别假设库里已有。
- 数据源会限流：所有请求走带 `Retry` 的 `FundAPI.session`，批量必须带 `delay>=0.2~0.3`。
- 免费实例（Render）冷启动时首个请求 3–4 秒，前端超时设置要留足。
- 历史接口分页有 `sleep(0.2)`，一次全量同步很慢，别放在同步 HTTP 请求里跑。

## 2026-09-26：入库侧的"防未来函数"门（净值不许签成还没到的那天）

上游会**预签发**净值行。实测 `000725`（大成添利宝货币B，货币型）：09-25 那天东财 lsjz 就把
`FSRQ` 给成 09-26 / 09-27（`DWJZ` 两条都是 0.3442），而同一只基金 07-31 那次也给过 08-01 / 08-02。
验证侧从第 13 轮起就有"不取目标日之后的行情"这道门，**入库侧一直没有** —— 于是脏数据是写入那一刻
进来的：一次「更新基金净值」往生产 `fund_history` 写了未来行，并把 `fund_info.nav_date` 也写成 09-27。

- **门在哪里**：`src/fund/fund_api.py:usable_history_rows()`（谓词 `is_future_nav`，按北京日
  `current_as_of()`）。挂在**两个取数入口**（`get_fund_history` / `get_fund_history_range`）上 ——
  三个 `FundHistory(...)` 写入点都在它们下游，所以只此一份实现；档案头那一处
  （`fund_sync_manager.update_all_funds_info` 里 `fund.nav_date = parsed_nav_date`）共用同一个谓词。
  丢弃必须说出来：`[净值门] <码> 上游给了 N 条晚于 <日期> 的净值行，已丢弃不入库`。
  判据 `tests/unit/test_nav_future_row_gate.py`（含"今天与昨天的行必须照旧入库"的防过宽对照）。
- **为什么"日期已被追平"不等于没事**：同步只补没有的日期、**不覆盖已有行**（覆盖就是
  `nav_rewritten` 那族 ⚠ 的成因，故意保留不可变性）⇒ 提前签发的行一旦落下，之后永远不会被修正。
  所以清理不能只看"晚于今天"，要按**写入时刻早于自己日期**这一族历史残留点名删。
- **清理工具**：`python scripts/drop_future_nav_rows.py`（默认只出计划、逐行列出是谁）。
  真删要 `--apply --confirm DROP-FUTURE-NAV --json <备份>`，备份含被删行原值 + 档案头前后值，
  可逐行插回；`--production` 沿用 `purge_junk_funds.py` 那把方向闸（旗子与实际连接不一致退 4），
  确认词的检查排在连库之前。判据 `tests/unit/test_drop_future_nav_rows.py`：dry-run 一行都不删、
  没备份就拒删、点名的日期库里没有就拒跑、档案头倒回真实末条、被点名的行进备份逐行清单。
- **本次执行回执**（生产，2026-09-26 00:0x 北京）：删除 4 行（`000725` 的 08-01 / 08-02 / 09-26 / 09-27），
  档案头 `nav_date 2026-09-27 → 2026-09-25`、`latest_nav → 0.3441`，备份
  `data/backups/nav_future_rows_20260926.json`；删后复核"提前签发行 0 条"，
  而 `已判 1190 / ⚠ 419 / 区间 34.37%~69.58%` 一个都没变（先量过：该码 2 条活预测、0 条拿这几天当端点）。
