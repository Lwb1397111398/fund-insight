# 板块与基金匹配

## 职责一句话
给定一个板块名（"半导体"、"恒生科技"、"豆粕"），决定用哪只**公募基金**作为该板块的验证标的，
并给出可复核的证据链（LLM 提了什么、抓到什么、为什么选它或为什么不选）。

## 运作流程
1. 入口：帖子分析时 `LLMAnalyzer._fill_fund_from_sector()` 给预测补基金；
   板块匹配页/批量任务时走 `POST /api/config/sector-mappings/ai-match`、`ai-batch`。
2. 核心：`src/services/sector_fund_agent.py` 的 `resolve_sector_fund(sector)` 按 T0→T5 跑：
   - **T0** 精确候选（已审查映射 + 内置字典精确键，短键不再做子串匹配）；
   - **T1** LLM 提案 3–5 只 + 关键词 + 别名；
   - **T2** 逐只抓站验证：是基金不是股票、抓得到净值（`is_strict_ok`）、
     LLM 声称名 vs 官方名（对不上只降级不淘汰，因为 LLM 常记错代码↔名称）、
     **宽基指数硬拒**（豆粕→中证500ETF 这类"拿大盘凑数"直接淘汰）；
   - **T3** LLM 语义复判 `suitable/proxy/score`，`score>=70` 才算相关；
   - **T4** 关键词搜索回环（`fund_api.search_fund`，结果天然只含基金）→ 回 T2/T3；
   - **T5** direct 全灭后才允许 **proxy（有意代理）**：老板确认过 `债券→国债ETF`、
     `SpaceX→军工ETF` 这类"没有对口基金，取关联度最大的替代"不是错配。
3. 产出 `SectorDecision`：`status ∈ matched|proxy|needs_review|conflict|no_fund`、
   `confidence`、逐轮 `evidence`。拿不准一律 `needs_review`，**不再随机填一只基金**。
4. 落库：`apply_decision()` 写 `sector_fund_mapping`（含 `match_source/match_kind/confidence/
   verified_at/verify_message/evidence/reviewed_by/owner_locked`），写完刷新两处进程内缓存。
   `owner_locked=1` 的行直接拒绝覆盖。
5. 影响谁：预测的验证标的、`FundSyncManager` 自动补基金、博主准确率统计。

## 关键数据结构
`sector_fund_mapping`：`sector_name`(非唯一) + `fund_code`(FK fund_info) + `reviewed` +
`match_source` + `match_kind(direct|proxy)` + `confidence` + `verified_at` + `verify_message` +
`llm_reason` + `is_fetchable` + `evidence`(JSON 文本) + `reviewed_by` + `owner_locked`。
`sector_alias`：`alias_name`(unique) → `sector_name`，`source` 标来源。

## 已知坑与约束
- **审查门禁不可作弊**：`reviewed=1` 必须有 `match_source + verified_at + confidence + verify_message`；
  `batch-review` 对无证据行默认拒绝（老板在弹窗明确确认时放行并记 `reviewed_by=owner`）。
  校验 SQL 要写 `confidence IS NULL OR ...`——`NULL < 0.85` 结果是 NULL，会把整条谓词短路掉。
- **不要用 `scripts/seed_sector_mappings.py`**：它会把内置板块直接标成 `reviewed=True`。
  要物化请用 `match_source='seed_builtin'` + `reviewed=false`。
- **两处进程内缓存**：`SectorFundService._cache` 与 `sector_fund_map._load_db_aliases()`，
  写完必须 `refresh_cache()` + `refresh_db_aliases_cache()`，否则"自己写的映射自己读不到"。
- **`get_fund_info` 的历史兜底**会让学生代码也"验证通过"，验证路径必须 `allow_fallback=False`。
- **`is_active=false` 不等于修好**：列表/verify-all/`sync_sector_mappings` 都按 `is_active=1` 过滤，
  置灰等于把问题藏起来。
- 帖子分析热路径默认 `SECTOR_AGENT_LLM_IN_POST=false`（只走确定性路径），重活交给批量任务。
- 单板块实测 4–25 秒（LLM + 多只抓站），`budget_ms` 默认 30s；`ai-batch` 的锁必须是 `RLock`
  （`start()` 持锁期间会调 `is_running()`，普通 Lock 会自锁死，实测挂住请求 60s）。

## 身份体检：证明"这个码就是名字里那只基金"（2026-09-21 新增）

入口：`src/services/sector_identity_audit.py`（判据）+ `scripts/sweep_sector_mappings.py`（体检/降级/回滚）。

**为什么"能抓到净值"完全不够**：6 位代码在 A 股与场外基金之间码段重叠。
`000725` 既是深市"京东方Ａ"也是货基"大成添利宝货币B"，`000938` 既是"紫光股份"也是
"华商稳固添利债券C"。旧 `verify_fund_fetchable` 的 `if ok: return 'fund'` 于是永远返回"基金"，
映射表里的股票行照样"验证通过"，预测拿货基净值去验证股票观点。

**判据（全部基金域自证，零 LLM、零股票域探测）**：

| 证据 | 来源 | 用途 |
| --- | --- | --- |
| 码→官方名 | `fund.eastmoney.com/js/fundcode_search.js`（1 请求 2.7 万条，`item[2]` 是中文名）→ 缺失时回落 `pingzhongdata/{code}.js` 的 `fS_name` | 判"这个码到底是哪只基金" |
| 名→域 | `fundsuggest` payload 的 `CATEGORYDESC`（`基金`/`深市`/`沪市`/`美股`…） | 判"这个名字是不是基金" |
| 站点负证据 | `pingzhongdata` 的 404 是 **HTTP 200 + 3924 字节**，按字节 `b'\xe9\xa1\xb5\xe9\x9d\xa2\xe6\x9c\xaa'` 判 | 区分"没有此码"与"请求失败" |
| 名字同一性 | `NFKC` 归一 + **字符集 Jaccard**（`jaccard_name`），阈值 0.35 | 同一只基金的正名/别名语序不同 |

verdict：`ok / not_a_fund / code_is_other_fund / wrong_code / not_fetchable / unknown / probe_unavailable`，
前四个不可服务；`unknown`、`probe_unavailable` **永不降级**（"没查到"不等于"查到了且不对"）。

## 本模块的坑（补充）

- **`search_fund` 是混合证券搜索**，且契约是 `None`=失败 / `[]`=查无。
  任何"拿它的结果当基金"的地方都必须先按 `is_fund` 过滤——前端"人工换一只"接口已过滤。
- **`is_fetchable` 的语义是"可服务"而不是"能抓到"**：NULL = 从没体检过（105 条历史行），
  谓词必须写成 `or_(is_(None), == True)`，否则一次改动就让历史映射集体消失。
- **`get_fund_by_sector` 命中缓存时根本不查库**，所以门禁要同时落在 `_load_cache`、
  两个 DB 分支和静态表 `SECTOR_FUND_MAP` 回落上；`sector_fund_agent.tier0()` 是第 9 条读者。
- **拒绝集按 (板块, 代码) 记，不能按代码**：`159819` 对"应用"是错的、对"AI"是对的。
- **查询名册/检索要用原始存名**，NFKC 只用于比较（`京东方Ａ` 原样查得到、归一后 0 命中）。
- **`is_etf` 要"场内码段 + 名含 ETF"两个条件**，且 `联接` 必须最先判（`162412 华宝医疗ETF联接A`
  含 ETF 又不是场内）；旧正则 `15[0-9]{3}` 只有 5 位，深市 15xxxx 一条都匹配不上。
- **归一化与阈值由 `tests/fixtures/name_identity_golden.json` 钉死**：
  id 79（纳指国泰 vs 纳斯达克）j=0.40、id 25（SpaceX 卫星ETF永赢）j=0.467 都贴着 0.35，
  抬阈值就会把正确行翻成硬拒。
- **`is_fetchable` 的镜像不变量**：`verdict ∈ 不可服务集合 ⇒ is_fetchable 必为 False`。
  SQL 读者只看列，所以每个写库出口（`apply_results`、`update_mapping`）都要重新物化它，
  `_mapping_eligible` 也额外认 verdict——否则 agent 换标的把列清成 NULL 就等于没防住。
- **老板锁定行不打"不可服务"章**：审查门禁连 `owner_confirm` 都拒绝不可服务行，
  若给 owner 行盖这个标记，老板自己选的代理就被永久关在门外（有单测锁住）。
- 体检脚本改完库要 `refresh_cache()`。**Web 与 Cron 是两个进程**：`_cache` 是类级缓存、
  带 60s TTL（`_CACHE_TTL`），所以 Cron 里跑的体检最多 60 秒后被 Web 进程看到；
  要立刻生效就重启 Web。

## 第 8 轮之后新增的四条硬规矩（改这一层前必须知道）

- **审查署名与锁定必须一致**：人在页面点「标记已审查」= 老板结论 →
  `reviewed_by='owner'` + `owner_locked=True`。以前 agent 行被点过之后留着
  `reviewed_by='agent'` 却拿到锁定，等于一边借 owner 分支绕过置信度门槛驱动改标，
  一边在回写报告里被说成"老板手定的有意代理"（实测 秦安股份 0.7975、硬件 0.755）。
- **审计回写端点的判据一律取"改之前"的行状态**，且所有拒绝判断做完才允许
  `ensure_fund_info_exists`（它内部 commit，先补档案再拒行 = 生产留下一只无人认领、
  却被同步任务拉净值的基金）。服务端四条线：总开关 `ENABLE_SECTOR_AUDIT_IMPORT`（默认关）、
  免疫不可从线上获得、写入前过基金域自证、落库前物化镜像不变量。
- **改预测必须带一次性 `run_id`**：`scripts/run_sector_sync.py` 现在拒绝复用旧 id
  （一个 id 挂两批 = 一条回滚命令退掉两批），UI 那条路也自动生成 id；
  回写生产前先跑 `scripts/snapshot_prod_mappings.py` 留前像。
- **净值补拉按"窗口内实际密度"判断，不能只看最早一天**（`fund_api.backfill_history_range`）：
  只看最早一天会让"首尾有、中间断"的洞永远补不上，实测卡住 80 条到期预测
  （生产同样中招，Cron 无限重试）。改完实测解锁 56 条，用例见
  `tests/unit/test_fund_history_backfill.py`。
- APK 是 WebView 壳（`BASE_URL` 默认指向线上站点，不打包前端资源），
  所以后端/前端改动**不需要**重出 APK，只要线上部署是新的。
