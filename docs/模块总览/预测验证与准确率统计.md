# 预测验证与准确率统计

## 职责一句话
用真实净值判断博主的预测对不对，并据此算出准确率、等级与博主排行——**这是全项目最需要谨慎的模块**。

## 运作流程
1. 触发：调度器 `src/tasks/scheduler.py`（本地）/ `scripts/run_scheduled_tasks.py daily`（Render Cron）、
   `POST /api/predictions/verify*`（手工/批量）、`prediction_verify_task.py`（后台任务状态 + 轮询）。
2. `prediction_verify_service.py`：取起点/终点净值 → 算区间涨跌幅、过程最大涨跌、回撤、
   命中峰值/低谷等过程指标 → 按预测方向与震荡阈值判 `is_correct`，写 `verify_score`、
   `verify_history`、`verified_at`，并把结论落到 `predictions.status`（`success|failed`）。
3. 台账：`prediction_change_logs`（不可变变更日志，含 `before_state/after_state`、`run_id`）；
   博主侧字段 `accuracy_rate/total_predictions/correct_predictions/total_verify_score/grade/archived_*`
   由 `src/utils/blogger_stats.py::recalculate_blogger_stats` 重算（**没有 blogger_stats 表**，
   统计列在 `bloggers` 上）。
4. 口径：`accuracy` 是 **0–100 的百分数**（不是 0–1 小数），分母只算
   `verify_count>0 AND is_deleted=false AND prediction_type!='flat'` + 归档计数；
   详见 `docs/ACCURACY_METRIC_SPEC.md`。

## 数据充分性门（`_check_fund_data_availability`，验证前必过）
按顺序返回 `reason`，**拒判时一条结论都不写**（`is_correct` 保持 NULL）：
1. `same_nav_endpoint`（S7-2）：反查起点日与目标日**各自实际**取到的净值日
   （`_real_nav_date`，一律 `nav_date <= 请求日`），两者相等且窗口内确有净值 ⇒
   涨跌幅必然为 0，那是"没有信息"不是"判错"。需要**两种证据之一**，且都不许靠日历猜
   （第 12 轮 MAJOR-3 撤掉了"到期超过上限即永久不可验"那条纯日历推断）：
   ① 目标日之后已有净值 ⇒ 目标日确是休市日；② 已按区间问过数据源并留下凭据。
   两者都没有时不判退化，报 `insufficient_points` 继续重试 —— "目标日就是今天、净值还没发布"
   是每个工作日的常态，也可能是我们自己的镜像坏了，不能提前下结构性结论。
   `nav_after_target` 这条存在性探测是全仓验证路径**唯一**读目标日之后数据的地方，
   只用来判断"是不是交易日"，不参与任何净值与涨跌幅计算。
2. `insufficient_points` / `no_history`：窗口内净值条数 < `VERIFY_MIN_DATA_POINTS`(=2)。
   提示语分两种：本地最新净值**晚于**窗口终点 ⇒ 缺的是目标日附近那段历史，
   明说"补拉最新数据补不到这个窗口"；确实落后 ⇒ 才说"请更新基金数据"。
2b. `no_source_history`（S7-2 / S7-b）：上一条只在"**问过数据源**"之后才算数 ——
   `src/fund/backfill_proofs.py` 往 `system_config` 存一条
   `nav_backfill_proof:<基金代码>` 的**逐次探测列表**（v2 格式；每次存区间 + 源端给了几条 +
   核验时间）。老的"区间并集"格式一律判不可信并丢弃 ⇒ 会重新问一次。
   **只有单次探测完整包含本次窗口且未过期才算盖住**；只有两边都是空答复、且相交/首尾相接的
   区间才允许合并（非空答复永不合并，否则等于把空洞拼成包络）。TTL：非空 7 天、空答复 2 天
   （防限流页被当成事实）。凭据数超上限时保留**最近问过**的那些（秒级时间戳会并列，
   故用微秒 + start 兜底排序），否则被丢的恰是每天要重问的老窗口。
