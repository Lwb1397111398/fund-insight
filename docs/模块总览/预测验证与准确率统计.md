# 预测验证与准确率统计

## 职责一句话
用真实净值判断博主的预测对不对，并据此算出准确率、等级与博主排行——**这是全项目最需要谨慎的模块**。

## 运作流程
1. 触发：调度器 `src/tasks/scheduler.py`（本地）/ `scripts/run_scheduled_tasks.py daily`（Render Cron）、
   `POST /api/predictions/verify*`（手工/批量）、`prediction_verify_task.py`（后台任务状态 + 轮询）。
2. `prediction_verify_service.py`：取起点/终点净值 → 算区间涨跌幅、过程最大涨跌、回撤、
   命中峰值/低谷等过程指标 → 按预测方向与震荡阈值判 `is_correct`，写 `verify_score`、
   `verify_history`、`verified_at`，并把结论落到 `predictions.status`（`success|failed`）。
3. 台账：`prediction_change_logs`（不可变变更日志，含 `before_state/after_state`、`run_id`）；
   博主侧字段 `accuracy_rate/total_predictions/correct_predictions/total_verify_score/grade/archived_*`
   由 `src/utils/blogger_stats.py::recalculate_blogger_stats` 重算（**没有 blogger_stats 表**，
   统计列在 `bloggers` 上）。
4. 口径：`accuracy` 是 **0–100 的百分数**（不是 0–1 小数），分母只算
   `verify_count>0 AND is_deleted=false AND prediction_type!='flat'` + 归档计数；
   详见 `docs/ACCURACY_METRIC_SPEC.md`。

## 关键数据结构
`predictions`：`status ∈ pending|success|failed`、`is_correct`、`verify_count`、`verify_score`、
`start_nav/start_nav_date/end_nav/current_nav`、`verify_history`(JSON)、`has_active_prediction`、
`is_deleted`、`target_date`。
`prediction_change_logs`：`action`、`source`、`changed_fields`、`before_state`、`after_state`、`run_id`。

## 数据充分性门（`_check_fund_data_availability`，验证前必过）
按顺序返回 `reason`，**拒判时一条结论都不写**（`is_correct` 保持 NULL）：
1. `same_nav_endpoint`（S7-2 新增）：反查起点日与目标日**各自实际**取到的净值日
   （`_real_nav_date`，一律 `nav_date <= 请求日`），两者相等且窗口内确有净值 ⇒
   涨跌幅必然为 0，那是"没有信息"不是"判错"。1 天期预测的目标日落在休市日时最典型。
2. `insufficient_points` / `no_history`：窗口内净值条数 < `VERIFY_MIN_DATA_POINTS`(=2)。
   提示语分两种：本地最新净值**晚于**窗口终点 ⇒ 缺的是目标日附近那段历史，
   明说"补拉最新数据补不到这个窗口"；确实落后 ⇒ 才说"请更新基金数据"。
2b. `no_source_history`（S7-2 / S7-b）：上一条只在"**问过数据源**"之后才算数 ——
   `src/fund/backfill_proofs.py` 往 `system_config` 存一条
   `nav_backfill_proof:<基金代码>` 的负凭据（问过的区间 + 源端给了几条 + 核验时间，TTL 7 天）。
   验证侧看到盖得住本窗口且未过期的凭据，就把原因换成 `no_source_history` 并在提示语里
   引凭据原文；补拉侧看到凭据就跳过重复请求（Cron 不再为源端根本没有的历史天天白跑）。
   源端"给了 1 条但窗口要 2 条"也要记 —— 再问一次还是那 1 条（158038 实测）。
3. `end_nav_too_old`：终点净值早于目标日 `VERIFY_MAX_END_NAV_AGE_DAYS`(=10) 天以上（force 也不放过）。
4. `exact_target` / `weekend_previous` / `waited_previous` 放行，`waiting_target_nav` 等待
   （`VERIFY_DATA_WAIT_DAYS`=2 个自然日内）。
分诊工具：`scripts/triage_unverifiable_predictions.py`（只读，逐行给出窗口点数、
两端实际净值日与终态分类）；假结论清理：`scripts/revert_degenerate_verdicts.py`
（默认只报告，`--apply` 才撤，且只撤"涨跌幅恒为 0 且终点用的就是起点那条"）。

## 已知坑与约束
- **只有 `is_correct IS NULL` 的行才会被 `verify_all_pending` 捞起**：改了 `fund_code` 后必须
  先调 `sync_sector_mappings`（内部 `_reset_verification()` 清 status/is_correct/start_nav/
  verify_count/verify_history 等）才会重验；否则要么什么都不发生，要么用**旧基金起点净值**
  配**新基金终点净值**算出垃圾涨跌幅。
- 重映射必须带 `run_id` 才能整批回滚；`add_prediction_change_log` 在字段无变化时**不落库**，
  所以"日志条数 == 改动条数"不是有效判据，要用 service 返回的 `details` 行数。
- 目前仓库里**没有任何代码读取 `before_state`**，"可回滚"要靠 `scripts/restore_prediction_batch.py`
  （按 `run_id` 整批还原）与 `scripts/revert_degenerate_verdicts.py`（落改前快照 JSON）实现，
  别口头宣称可回滚。
- `end_nav_date` 从 S7-2 起存**实际净值日**，不再存请求的目标日；老数据里周末目标日的
  `end_nav_date` 仍是那个"根本不存在的日期"，跨这批数据做统计时要留意。
- 清理任务会连带删除变更日志（`retention_cleanup_service.py`），跑批量重映射的窗口要关清理。
- 统计是增量更新的（`_update_blogger_accuracy`），批量改预测后必须 `recalculate_blogger_stats`
  全量重算，否则分母被撑大、准确率双计。
- 该文件是 AGENTS.md 标注的高风险区：改前先跑
  `pytest tests/unit/test_prediction_verify_batch_task.py tests/unit/test_prediction_stats_is_correct.py
  tests/unit/test_prediction_maintenance.py tests/unit/test_prediction_lifecycle.py -q`。
