# 预测验证与准确率统计

## 职责一句话
用真实净值判断博主的预测对不对，并据此算出准确率、等级与博主排行——**这是全项目最需要谨慎的模块**。

## 运作流程
1. 触发：调度器 `src/tasks/scheduler.py`（本地）/ `scripts/run_scheduled_tasks.py daily`（Render Cron）、
   `POST /api/predictions/verify*`（手工/批量）、`prediction_verify_task.py`（后台任务状态 + 轮询）。
2. `prediction_verify_service.py`：取起点/终点净值 → 算区间涨跌幅、过程最大涨跌、回撤、
   命中峰值/低谷等过程指标 → 按预测方向与震荡阈值判 `is_correct`，写 `verify_score`、
   `verify_history`、`verified_at`，并把结论落到 `predictions.status`（`success|failed`）。
3. 台账：`prediction_change_logs`（不可变变更日志，含 `before_state/after_state`、`run_id`）；
   博主侧字段 `accuracy_rate/total_predictions/correct_predictions/total_verify_score/grade/archived_*`
   由 `src/utils/blogger_stats.py::recalculate_blogger_stats` 重算（**没有 blogger_stats 表**，
   统计列在 `bloggers` 上）。
4. 口径：`accuracy` 是 **0–100 的百分数**（不是 0–1 小数），分母只算
   `verify_count>0 AND is_deleted=false AND prediction_type!='flat'` + 归档计数；
   详见 `docs/ACCURACY_METRIC_SPEC.md`。

## 数据充分性门（`_check_fund_data_availability`，验证前必过）
按顺序返回 `reason`，**拒判时一条结论都不写**（`is_correct` 保持 NULL）：
1. `same_nav_endpoint`（S7-2）：反查起点日与目标日**各自实际**取到的净值日
   （`_real_nav_date`，一律 `nav_date <= 请求日`），两者相等且窗口内确有净值 ⇒
   涨跌幅必然为 0，那是"没有信息"不是"判错"。需要**两种证据之一**，且都不许靠日历猜
   （第 12 轮 MAJOR-3 撤掉了"到期超过上限即永久不可验"那条纯日历推断）：
   ① 目标日之后已有净值 ⇒ 目标日确是休市日；② 已按区间问过数据源并留下凭据。
   两者都没有时不判退化，报 `insufficient_points` 继续重试 —— "目标日就是今天、净值还没发布"
   是每个工作日的常态，也可能是我们自己的镜像坏了，不能提前下结构性结论。
   `nav_after_target` 这条存在性探测是全仓验证路径**唯一**读目标日之后数据的地方，
   只用来判断"是不是交易日"，不参与任何净值与涨跌幅计算。
2. `insufficient_points` / `no_history`：窗口内净值条数 < `VERIFY_MIN_DATA_POINTS`(=2)。
   提示语分两种：本地最新净值**晚于**窗口终点 ⇒ 缺的是目标日附近那段历史，
   明说"补拉最新数据补不到这个窗口"；确实落后 ⇒ 才说"请更新基金数据"。
2b. `no_source_history`（S7-2 / S7-b）：上一条只在"**问过数据源**"之后才算数 ——
   `src/fund/backfill_proofs.py` 往 `system_config` 存一条
   `nav_backfill_proof:<基金代码>` 的**逐次探测列表**（v2 格式；每次存区间 + 源端给了几条 +
   核验时间）。老的"区间并集"格式一律判不可信并丢弃 ⇒ 会重新问一次。
   **只有单次探测完整包含本次窗口且未过期才算盖住**；只有两边都是空答复、且相交/首尾相接的
   区间才允许合并（非空答复永不合并，否则等于把空洞拼成包络）。TTL：非空 7 天、空答复 2 天
   （防限流页被当成事实）。凭据数超上限时保留**最近问过**的那些（秒级时间戳会并列，
   故用微秒 + start 兜底排序），否则被丢的恰是每天要重问的老窗口。
   数据源调用 `get_fund_history_range` 用**返回 `None`** 表达"这次没问到"（超时、非 JSON、
   `ErrCode≠0`、`Data` 不是 dict、`LSJZList` 缺失或不是列表、有行解析失败、
   翻页未取满 `TotalCount`、没有 `TotalCount` 又没翻到底）；实测线上"真无数据"是
   `Data` 为 dict + `LSJZList: []` + `ErrCode=0` + `TotalCount=0`，两者必须分开。
   凭据写进**调用方的会话并只 flush**（所以调用方 `rollback` 时凭据一起消失，SQLite/PG 一致。
   第 12 轮 MAJOR-5 指出用 SAVEPOINT 反而破这个一致性：SQLite 上"无外层事务时
   SAVEPOINT 自己就是事务"，RELEASE 等于提交）。因为 flush 后对象不在 `new/dirty` 里，
   它用 `db.info['proof_writes']` 告知调用方"这次真写了东西"，验证侧据此提交。
   遗留（待 PG 实测）：并发首次插入会撞 `config_key` 唯一约束、PG 会 abort 事务；
   现在靠 `prediction_verify_task` 的进程锁 + advisory lock 保证同时只有一个批量进程，
   真要放开并发得改成 `ON CONFLICT DO UPDATE`。
   窗口点数、`get_nav_history` 的过程指标、"该基金最新到哪一天"都**一律查 DB**，
   不吃 `_history` 缓存（缓存只装 ±120/14 天，部分命中会把点数与 `peak_hit_ratio` 算少
   ⇒ Cron 与手动按钮能判出相反结论，第 12 轮 MAJOR-6）。
   补拉侧配套：短窗口免打接口的条件从"起点被覆盖 + 窗内有 1 条"加严成
   **终点那天也有净值行**，否则"目标日缺行"的窗口永远问不到凭据（MAJOR-3）。
   源端给过几条但本地仍凑不够时措辞是"已按区间要过、需按区间重放补拉"，不写成"拿不到"。
3. `end_nav_too_old`：终点净值早于目标日 `VERIFY_MAX_END_NAV_AGE_DAYS`(=10) 天以上（force 也不放过）。
4. `exact_target` / `weekend_previous` / `waited_previous` 放行，`waiting_target_nav` 等待
   （`VERIFY_DATA_WAIT_DAYS`=2 个自然日内）。
分诊工具：`scripts/triage_unverifiable_predictions.py`（只读，逐行给出窗口点数、两端实际净值日、
终态分类，并报"日历口径 vs 验证服务 reason"不一致的行）。假结论清理：
`scripts/revert_degenerate_verdicts.py`（默认只报告，`--apply` 才撤；判据是**净值值 + 日期
双锚定**，并要求"起点之后到目标日之间没有任何净值行"，以挡住两天数值恰好相同的真平盘）。
`POST /api/predictions/rollback-invalid` 真写必须带 `ids=`（就是预览里列出的那几条）；
不限定 id 的全库回溯只能在脚本里显式 `allow_full_sweep=True`。

## 已知坑与约束
- **只有 `is_correct IS NULL` 的行才会被 `verify_all_pending` 捞起**：改了 `fund_code` 后必须
  先调 `sync_sector_mappings`（内部 `_reset_verification()` 清 status/is_correct/start_nav/
  verify_count/verify_history 等）才会重验；否则要么什么都不发生，要么用**旧基金起点净值**
  配**新基金终点净值**算出垃圾涨跌幅。
- 重映射必须带 `run_id` 才能整批回滚；`add_prediction_change_log` 在字段无变化时**不落库**，
  所以"日志条数 == 改动条数"不是有效判据，要用 service 返回的 `details` 行数。
- 目前仓库里**没有任何代码读取 `before_state`**，"可回滚"要靠 `scripts/restore_prediction_batch.py`
  （按 `run_id` 整批还原）与 `scripts/revert_degenerate_verdicts.py`（落改前快照 JSON）实现，
  别口头宣称可回滚。
- `end_nav_date` 从 S7-2 起存**实际净值日**，不再存请求的目标日；老数据里周末目标日的
  `end_nav_date` 仍是那个"根本不存在的日期"，跨这批数据做统计时要留意。
- 清理任务会连带删除变更日志（`retention_cleanup_service.py`），跑批量重映射的窗口要关清理。
- 统计是增量更新的（`_update_blogger_accuracy`），批量改预测后必须 `recalculate_blogger_stats`
  全量重算，否则分母被撑大、准确率双计。
- 该文件是 AGENTS.md 标注的高风险区：改前先跑
  `pytest tests/unit/test_prediction_verify_batch_task.py tests/unit/test_prediction_stats_is_correct.py
  tests/unit/test_prediction_maintenance.py tests/unit/test_prediction_lifecycle.py -q`。

- "撤结论"有两个不同语义，别混用：**`rollback_invalid_verifications`**＝"今天的数据已不支撑这条
  结论"（只撤判不过门的行）；**`scripts/revert_degenerate_verdicts.py`**＝"结论当初就是用错的/
  未来的数据判出来的"（退化终点、或 `end_nav_date > target_date` 的未来函数结论，实测 94 条）。
  两者的清零字段共用 `clear_verification_fields()`，只此一处定义。
  教训：拿前者去撤后者，94 条里只撤掉 1 条（其余今天仍可验，被算成"保留"）。
- `verify_history` 在库里是**追加序**，API 出口（`get_detail` / `_serialize`）倒序返回，
  因为前端"本次验证详情"19 处绑定读 `[0]`。别往里面塞"墓碑"条目——历史表按
  `is_correct ? '正确':'正确'`/`score || 0` 渲染，会凭空多出一条假的"验证失败/0 分/错误"。
- 预热缓存 `_nav_cache['_history']` 存的是 `(nav_date, nav)` 元组，不是 ORM 实例：
  `SessionLocal` 未设 `expire_on_commit=False`，而批量路径每条预测都会 commit（进度上报），
  存实例会让预热翻转成 N+1 放大器。

### 2026-09-22（第 15 轮）新增的四条硬约束

- **快照必须 deepcopy 可变值**：`verify_history` 是 JSON 列，验证路径用 `list.append`
  **原地**改它，而 `_json_value` 曾经直接把那个 list 对象塞进快照 ⇒ `before_state` 与
  `after_state` 是同一个对象，"变更前历史"其实是变更**之后**的、`changed_fields` 永远
  报不出 `verify_history`（第 1 轮验证是 `[]`→非空的重新赋值，所以前像碰巧对；
  第 2 轮起才说谎）。还原清单今天收进了 `verify_history`，不 deepcopy 就会从"审计说谎"
  变成"还原写回错数据"。测试必须用 `.append()` 形态，写成重新赋值挡不住。
- **字段清单只有一处**：`clear_verification_fields()`（16 个字段，本轮补 `ai_judgment`）
  与 `restore_prediction_batch.RESTORE_FIELDS`（还原清单）。真实教训：一次事故还原脚本
  自己手抄了一份清单、漏 `verify_score` ⇒ 11 行"结论 True 配 49 分、台账 100 分"，
  漂移闸门据此报出唯一那条未解释漂移。现在修复脚本 import 那份唯一清单，
  `tests/unit/test_verdict_field_restore_roundtrip.py` 用"记录被写过的字段名"的哨兵对象
  钉住两份清单不许分叉，并禁手抄（AST 查本地赋值）。
  存量对账：`python scripts/resync_verdict_scalars.py`（默认 dry-run；只按台账末条同步
  `verify_score`，证据互相矛盾的行只报不改并 exit 3）。
- **`current_nav_date` 与 `end_nav_date` 同口径**：都写**实际用到**的那一天（目标日落在
  休市日时是前一个交易日），不再写请求日。同一端点在两个字段里给两个日期，会让
  "两端日期可对比"这条审计假设失效。
- **漂移闸门的 `--offline` 语义 = 只复现确定性判据**：既桩数据源补拉、也桩
  `PredictionVerifyService.llm_analyzer`，否则"未解释漂移=0"取决于有没有 LLM 密钥
  （边界分/阈值附近/方向相反这三类都会去问 LLM 改判，全库末轮 `llm_verify` 有 15 行）。
  副本保护从"问一句新工厂绑在哪"（同义反复）升级为两道：扫描 `sys.modules` 里**所有**
  `SessionLocal` 引用是否都指向副本（`src/fund/fund_api.py` 等都是模块级 import，正是
  那次误写镜像库的形态），以及开跑前后对源库算 `size + sha256`，变了就 exit 6。
