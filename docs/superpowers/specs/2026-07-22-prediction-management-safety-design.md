# 预测管理安全重构设计

## 目标

在不丢失 Supabase 生产资料、不改变预测评分规则的前提下，修复预测管理的数据正确性问题，并把日常管理、批量验证和高风险维护操作拆分为清晰边界。

## 已确认问题

- 普通删除执行物理删除，与模型软删除字段和产品可追溯原则冲突。
- 相似预测合并允许跨博主、空基金代码分组，可能破坏博主归属和统计。
- 修改预测周期不会重算目标日期；已验证预测仍可直接修改关键字段。
- 板块映射同步使用过时状态值判断，已验证预测可能换基金但保留旧验证结果。
- 批量验证状态只存在 Render 进程内，重启、多实例和 Cron/Web 并发时不可靠。
- 列表最多拉取 1000 条并在浏览器筛选，记录增长后会产生不可见数据和错误计数。
- 项目缺少正式数据库迁移流程，不能直接依靠 `create_all()` 更新 Supabase。

## 设计决策

1. 原始预测默认永久保留，删除改为可恢复归档；不再自动合并预测。
2. 日常页面只提供查看、筛选、编辑待验证预测、归档和触发验证。
3. 重复检查、映射同步和验证回溯移入维护区，统一采用预览和确认执行两阶段。
4. 数据库存储状态继续兼容 `pending/success/failed`，API 提供更清晰的生命周期和结果字段，避免破坏历史数据。
5. 已验证预测的方向、基金和周期不可原地修改；后续纠正必须保留修改快照并重新验证。
6. 验证结果、验证历史和博主统计在同一事务中提交；批量任务状态写入数据库。
7. Supabase 结构变更使用显式 Alembic 迁移，Web 启动不自动执行迁移。

## 数据安全

生产执行顺序固定为：只读盘点、`pg_dump`、应用 JSON 导出、隔离库恢复校验、迁移预检、人工确认、生产迁移、行数与统计复核。任何历史恢复、映射重绑或批量回溯都必须先输出影响清单，不在普通部署过程中执行。

## 兼容策略

现有预测列表的 `data` 数组和主要端点保留；新增分页元数据、恢复接口和维护预览接口。旧的高风险执行接口先改为安全默认并标记废弃，不在首个版本直接删除。

## 验收标准

- 普通预测操作不再物理删除资料。
- 跨博主预测不会被自动合并。
- 修改周期后目标日期一致，已验证关键字段不能静默变化。
- Cron 与 Web 同时触发时，同一预测只完成一次验证和一次统计增量。
- 超过 1000 条记录仍可完整分页、筛选和统计。
- SQLite/PostgreSQL 兼容测试、专项 pytest、全量 pytest 和初始化检查通过。
- 生产迁移前完成可恢复备份演练；未确认时不连接或写入 Supabase。
